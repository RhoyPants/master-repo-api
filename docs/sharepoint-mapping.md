# SharePoint mappings

Signed-in users can open **Mappings → SharePoint Mapping** in the header (`/sharepoint-mapping`). This internal tool does not restrict mapping access by role. Choose an existing module template or create a new module, select a staging table, and enter a SharePoint site ID. Its lists load automatically into a searchable **SharePoint list** dropdown. Select by list name; only the stable list ID is stored in JSON. Selecting another list automatically reloads its columns. **Refresh lists** reloads discovery after a list is added or renamed. Changing the site clears the previous list selection, and discovery errors do not silently change a saved list ID. Existing templates load their columns automatically. Expand **Source & destination** to edit the connection or matching keys. Field dropdowns show both display names and stable internal names. Use a row's **Edit** button for fixed values, value rules, or lookup settings. The backend discovers SQL columns and Graph list columns; credentials remain in the API environment.

Pair source columns to destination fields and choose copy, case conversion, trimming, number/boolean conversion, fixed values, UUID generation, value rules, or staging-table lookups. Each field can apply to creates, updates, or both. Equality filters limit eligible source rows. The source record key identifies selected rows in existing sync screens; the destination matching field determines insert versus update. These keys can be different columns (for example, Item Class records are selected by `ItmsGrpCod`, but SharePoint matches their initials in `Code`).

For **Table lookup → Edit**, choose **Lookup database: Local / Item Master**, then a table, match column, and return column from that database. Changing the database clears the table and columns; changing the table clears the columns. Item Master uses the existing API environment connection, never credentials entered in the mapping. Each lookup saves an optional `lookup.database` (`local` or `itemmaster`); older mappings without it remain Local. Preview, save validation, sync execution, JSON import/export, and version history retain this selection. The shared SAP and Item Master mapping editors support the same lookup selector. Schema/connection errors are shown with retry controls and never switch the database automatically. The API account needs SELECT and schema-read access on the chosen database. Read-only discovery endpoints are `GET /api/mappings/lookup/tables?database=local|itemmaster` and `GET /api/mappings/lookup/columns?database=local|itemmaster&table=schema.table`; omitting the database selects Local, while unsupported database values are rejected.

Lookup regression checks: `node --test tests/mapping-lookup-databases.test.cjs tests/sap-mapping-sources.test.cjs`. Optional `node tests/mapping-lookup-databases.browser.cjs` uses the browser setup described below and mocked API responses to verify switching databases, cleared dependent selections, errors/retries, preview/save/reload, and version history without live writes.

The main action bar stays pinned below the workspace header while the page scrolls, keeping **Validate & preview**, **Save mapping**, and **Run saved mapping** accessible. **More actions** contains version history, reloading saved configuration, and JSON view/export/import tools. Refresh schema columns inside **Source & destination**. The enable-for-sync switch is grouped with module details and takes effect after saving. Field mappings grow with the page (no internal vertical scrolling); **Add field** sits below the last row. Column widths fit the available desktop space without unnecessary horizontal scrolling. Narrow screens retain horizontal table scrolling.

Use **Validate & preview** to inspect up to five source rows and both create/update payloads without writing to SharePoint. Preview results and **Save mapping** feedback open in a shared reusable result modal, including loading states and errors. Close the modal after the operation finishes to return to editing. Saving persists configuration only; it does not run a sync. Save as a draft first, or enable the mapping to use it for sync. Configuration is stored as JSON in `dbo.IntegrationMappings`, with provider, module, version, editor, and timestamp. Export/import uses schemaVersion 1 JSON; imports start as unsaved drafts. Concurrent saves return HTTP 409 instead of overwriting another editor's changes.

Enabled mappings replace the built-in mapping for the existing `/sync/staging-sharepoint/{module}/run`, `/run/single`, and `/run/multiple` URLs. Existing modules are `warehouse`, `item-class`, `item-group`, `item`, and `uom`. New modules can run from the mapping screen. Disabled/unsaved mappings preserve the existing built-in service. Disabling does not cancel an already-running sync. A run snapshots the saved configuration and records its version in the audit log.

## Mapping version history

Open **More actions → Version history** for a saved module to select a version in a read-only modal. A readable summary shows the mapping name, source table and matching keys, followed by field-mapping and source-filter tables. Each field shows its transformation, create/update write mode, and fixed values, value rules, or SQL lookup details where applicable. Expand **SharePoint connection details** for saved site/list IDs. Enabled/draft status, editor, and saved timestamp remain visible. The viewer uses saved internal names without live schema discovery, so historical mappings remain viewable after schema changes. Raw JSON is not shown in history; the editor's separate **View JSON** action is unchanged. History lists the newest versions first, with **Load older versions** for additional pages. Viewing history does not change the current mapping, discard unsaved edits, restore a version, or run a sync.

Every successful save atomically updates the current mapping and appends an immutable snapshot in `dbo.IntegrationMappingVersions`. Failed/conflicting saves do not create a version. Sync audit logs still record which mapping version a run used; configuration history records saves, including saves that were never synced.

The history migration seeds only the currently stored version of each existing mapping. Older overwritten JSON is not recoverable unless exported or backed up. `GET /api/mappings/sharepoint/{module}/history` lists up to 20 version summaries (`beforeVersion` pages older results); `GET /api/mappings/sharepoint/{module}/history/{version}` returns the saved snapshot without live schema validation.

Before any SharePoint write, the engine revalidates the live schema, all eligible source values, lookup results, duplicate source and transformed destination keys, and duplicate destination keys. Rows are matched by normalized key (trimmed, case-insensitive). It creates missing records, patches changed mapped fields, and skips unchanged rows; it never deletes records. Update requests use the existing item's eTag when available. Per-record failures and counts are stored using the existing audit tables. Configured runs for the same list are serialized within one API process (a second run returns 409). Uniqueness on the SharePoint matching field is recommended as a final protection against other API instances and external writers.

## Database setup

Apply `prisma/migrations/20261107090000_integration_mappings/migration.sql` using the project's normal migration workflow. It creates only `IntegrationMappings` and does not modify existing data. Check `npx prisma migrate status` before deploying migrations; do not blindly apply historical migrations to an existing database that has not been baselined. No generated Prisma client update is required by this feature: mapping persistence uses parameterized queries so the running API can use its current client. The Prisma model documents the table for future client generation.

Also apply `prisma/migrations/20261107171000_mapping_version_history/migration.sql` before deploying version-history code. It creates `IntegrationMappingVersions` and copies existing current configurations into history without modifying the current mappings. On a correctly baselined database, use `npx prisma migrate deploy`. The API account needs SELECT/INSERT access on the history table. A missing history table explicitly blocks saves rather than silently saving without a history snapshot.

The API account needs schema read, SELECT on the mapped staging/lookup tables, and read/write on mapping and audit tables. SharePoint uses the existing app registration. Graph list discovery/schema reads require site read permission; synchronization requires site write permission, including any required site-specific grants.

## Limits

- This editor implements staging → SharePoint. [SAP → staging mapping](sap-staging-mapping.md) supports the four existing SAP sync modules using the same editor and provider-isolated history. Other directions and AIMS mappings remain future work.
- Supported SharePoint field types: text, single choice, number, currency, boolean, and date/time. Read-only, calculated, multi-choice, person, taxonomy, native SharePoint lookup, and other complex types are shown as unavailable. The editor's table lookup rule resolves scalar values from Local SQL staging or the configured Item Master database; it is not a SharePoint lookup-column writer.
- SQL tables are discovered dynamically, excluding authentication, audit, migration, and configuration tables. No arbitrary SQL or JavaScript can be entered. Schema/table/column identifiers are checked against actual metadata; values are parameterized.
- Preview samples five rows. Execution validates all matching source rows before writing. Source rows and destination items are currently loaded into memory; paging uses Graph next links. Large datasets need a batched execution strategy.
- Display-name renames do not affect internal names. Removed columns, newly required fields, or changed types block validation until they are remapped.
- Existing data screens still use their original query services and columns. Changing a mapping's destination does not reconfigure those read screens.

Reference: [Graph list columns](https://learn.microsoft.com/en-us/graph/api/list-list-columns?view=graph-rest-1.0), [column definitions](https://learn.microsoft.com/en-us/graph/api/resources/columndefinition?view=graph-rest-1.0), [updating field values](https://learn.microsoft.com/en-us/graph/api/listitem-update?view=graph-rest-1.0).

Validation: `npm run build` and `node --test tests/mappings.test.cjs tests/mappings-engine.test.cjs tests/mappings-store.test.cjs` in the API; `npm run lint` and `npm run build` in the UI. Optional `node tests/mappings.live.cjs` checks the running API and live schemas read-only. `node tests/mappings.browser.cjs` uses a temporary Playwright Core installation and headless Edge to test discovery, preview, import, persistence, version conflicts, and saved version selection; it creates and removes only its own disabled draft mapping and history. `node tests/mappings-modals.browser.cjs` uses the same browser setup with mocked API responses to check preview/save/history modals, paging, loading, empty results, errors, retries, and unchanged save behavior without database or SharePoint writes.
